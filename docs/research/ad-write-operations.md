## Answer in brief

1. **Every AD write is a plain LDAP Add, Modify, ModifyDN or Delete.** There are no "action" endpoints. The meaning lives in which attribute is touched and with what value: `unicodePwd` replace = reset [S1]; `pwdLastSet` = 0 forces change [S5]; `lockoutTime` = 0 unlocks [S5]; `userAccountControl` bit 0x2 = disabled [S4]; remove `isDeleted` + replace `distinguishedName` = undelete [S8]. So the server's capability gate has to sit on **(operation × attribute × target)**, not on the LDAP verb. A generic "modify attribute" tool would bypass every gate below.
2. **Delegated rights are what bound the blast radius in AD, and the coarse built-in grants are a trap.** "Write Account Restrictions" (the property set that covers `userAccountControl` and `pwdLastSet`) also covers `msDS-AllowedToActOnBehalfOfOtherIdentity` (resource-based constrained delegation) on Server 2012+ [S6]. A service account delegated "enable/disable users" via that property set can also configure RBCD, which is a known takeover path (inference). Delegate per-attribute (`userAccountControl`, `pwdLastSet`, `lockoutTime`), not the property set.
3. **Tier 0 protects itself, partly.** Members of protected groups get their ACL overwritten from AdminSDHolder every 60 min by SDProp on the PDC emulator, with inheritance disabled [S11]. So OU-level delegation to the service account **does not** reach Domain Admins and similar. That is a useful built-in fence, but the server should not rely on it alone: four operator groups can be excluded via `dSHeuristics` [S11], and the service account might be over-privileged. The server should refuse writes to protected objects (and membership changes in protected groups) itself.
4. **No AD write takes an idempotency key, but LDAP gives two tools that make most writes safe to reason about.** (a) `LDAP_SERVER_PERMISSIVE_MODIFY_OID` (1.2.840.113556.1.4.1413) makes add-existing-value and delete-missing-value succeed, so group add/remove converges [S7]. (b) A single Modify is atomic and a delete of a specific value that is not present fails [S18], so "delete old value, add new value" in one request is a **compare-and-swap** for single-valued attributes like `userAccountControl` and `gPLink` (inference from [S18]). Creates, moves, deletes and restores are not idempotent: a retry after a lost response gets `entryAlreadyExists` / `noSuchObject`, so the server must re-read by `objectGUID` to learn what happened, never retry blindly.
5. **The biggest blast radius is not in AD at all, it is the sync cascade.** With Connect Sync, moving or renaming an OU, or moving objects out of a synced OU, makes the sync engine delete their Entra counterparts on its next cycle; the only brake is the 500-object accidental-delete threshold [S16]. A single-object move can silently delete one cloud user (with its licences and cloud group memberships) without tripping that threshold (inference). AD disables and deletes also flow to Entra on the next cycle (30 min Connect Sync, 2 min Cloud Sync, see [hybrid-sync.md](hybrid-sync.md)).
6. **Passwords need an encrypted LDAP connection.** `unicodePwd` can only be written over 128-bit TLS (LDAPS or StartTLS) or SASL-layer encryption (Kerberos/NTLM sealing) [S1]. Plain-text LDAP binds without sealing cannot reset passwords at all, which settles part of the transport question for #12's dependents.

## Operation inventory

Columns: **Mechanics** = the LDAP request. **Rights** = what the bind account needs on the target (beyond read). **Idem.** = what a retry does. **Blast** = what goes wrong if the client is wrong.

### Account state (users and computers)

| Operation | Mechanics | Rights | Idem. | Blast |
|---|---|---|---|---|
| **Disable** | Modify `userAccountControl`: set bit `ACCOUNTDISABLE` 0x2 [S4]. Full-value replace, so it is read-modify-write. Use delete-old/add-new CAS (inference from [S18]). | Write property `userAccountControl` (in Account Restrictions set [S6]) | Converges (bit already set) | **Medium.** Locks a person or a service out; a disabled computer stops authenticating to the domain (inference). The DC itself refuses this on Administrator (RID 500) and krbtgt: "userAccountControl MUST NOT contain the UF_ACCOUNTDISABLE bit if the RID … DOMAIN_USER_RID_ADMIN or DOMAIN_USER_RID_KRBTGT" [S2 #22]. Flows to Entra `accountEnabled` on next sync (inference, see hybrid-sync). |
| **Enable** | Clear bit 0x2 the same way | Same | Converges | **Medium.** Re-opens a dormant account. A freshly created user with no password may also carry `PASSWD_NOTREQD` 0x20 (inference); enabling that is a hole. |
| **Unlock** | Modify `lockoutTime` = 0. "A value of zero means that the account is not currently locked out" [S5]; AD accepts only 0 as a client-written value (inference, commonly documented, not stated on [S5]). | Write property `lockoutTime` (in no property set, [S5] shows no attributeSecurityGuid) | Converges | **Low.** Lockout is processed on the PDC emulator [S15]; write to the PDC so the unlock is seen at once (inference). |
| **Must change at next logon** | Modify `pwdLastSet` = 0. "If this value is set to 0 and the User-Account-Control attribute does not contain the UF_DONT_EXPIRE_PASSWD flag, then the user must set the password at next logon" [S5]. Clearing it = write -1, which the DC turns into "now" (inference, common practice). | Write property `pwdLastSet` (Account Restrictions [S6]) | Converges | **Low.** No effect if `DONT_EXPIRE_PASSWORD` 0x10000 is set [S5]. |
| **Account expiry** | Modify `accountExpires` (FILETIME, 0 or 0x7FFFFFFFFFFFFFFF = never) (inference) | Write property `accountExpires` (Account Restrictions [S6]) | Converges | Low. Administrator must have `accountExpires` = 0 [S2 #15]. |
| Other UAC bits | `DONT_EXPIRE_PASSWORD`, `PASSWD_NOTREQD`, `DONT_REQ_PREAUTH`, `USE_DES_KEY_ONLY`, `TRUSTED_FOR_DELEGATION`, `TRUSTED_TO_AUTH_FOR_DELEGATION`, account-type bits [S4] | `TRUSTED_FOR_DELEGATION` additionally needs **SeEnableDelegationPrivilege** on the DC, held by Administrators by default [S14] | — | **Critical.** `DONT_REQ_PREAUTH` enables AS-REP roasting; delegation bits let a service impersonate anyone [S14]; flipping between `NORMAL_ACCOUNT` and `WORKSTATION_TRUST_ACCOUNT` is constrained [S2 #21]. **Do not expose.** The server should only ever change bit 0x2 (and maybe 0x10000) and preserve the rest. |

### Passwords

| Operation | Mechanics | Rights | Idem. | Blast |
|---|---|---|---|---|

### Group membership

| Operation | Mechanics | Rights | Idem. | Blast |
|---|---|---|---|---|
| **Add / remove member** | Modify `member` add/delete value (the member's DN; `<GUID=…>` / `<SID=…>` DN forms avoid rename races (inference)). With `PERMISSIVE_MODIFY` the request "MUST succeed even if it attempts to add a value already present … or remove a value not present" [S7]. | Write property `member` on the **group** (not on the user) (inference, standard delegation) | Converges with permissive modify; without it a retry gets `attributeOrValueExists` / `noSuchAttribute` | **Varies by group, and this is the main escalation path.** Adding to a protected group (Domain Admins, Enterprise Admins, Administrators, Account/Backup/Print/Server Operators, Schema Admins, Key Admins, …) [S11] is tier-0 escalation. Adding to a group that is ACL'd onto GPOs, file shares, a PSO [S13] or a privileged Entra role via sync (inference) has the same shape one step removed. Adding a user to a group that is a member of a protected group makes it protected too (SDProp works on transitive membership [S11]). |

### Object lifecycle: create, rename, move, attribute edit

| Operation | Mechanics | Rights | Idem. | Blast |
|---|---|---|---|---|
| **Create user** | Add `objectClass=user`, `sAMAccountName` (≤ 20 chars, no `"/\[]:|<>+=;?,*`, not ending in `.` [S2 #8-12]), `userPrincipalName`, then set password and enable in a second Modify (inference: the password cannot be set before the object exists, so create disabled, set password, then enable). | Create Child (user) on the OU; plus the password/UAC rights above | **No.** Retry gets `entryAlreadyExists`; the server cannot tell "mine" from "pre-existing" except by re-reading and comparing `whenCreated`/`objectGUID` (inference). | **Low-medium.** Creates a new principal; if the OU is in sync scope it appears in Entra on the next cycle. |
| **Create computer (pre-stage)** | Add `objectClass=computer`, `sAMAccountName` ending in `$` [S2 #11], `userAccountControl` = `WORKSTATION_TRUST_ACCOUNT` 0x1000 [S4] | Create Child (computer) on the OU. Separately, any authenticated user can create up to `ms-DS-MachineAccountQuota` (default 10) computers by domain join [S17]. | No (as above) | **Low-medium.** A pre-staged computer account is a principal someone can later join as (inference). |
| Create group | Add `objectClass=group`, `groupType`, `sAMAccountName` (≤ 256 chars [S2 #13]) | Create Child (group) | No | Low |

| **Move within a domain** | ModifyDN with `newSuperior` | Delete Child on the source container (or Delete on the object) + Create Child on the target (inference, standard AD move rights) | Retry → `noSuchObject` | **Medium-High.** Changes which GPOs apply (inherit from new OU), which delegations apply, and sync scope: an object moved out of a synced OU is deleted in Entra next cycle; under 500 objects no brake fires [S16]. | Move across domains | ModifyDN with `LDAP_SERVER_CROSSDOM_MOVE_TARGET_OID` naming the target DC [S7]; must be sent to the **source domain's RID master** [S10]. Refused for: RID ≤ 1000, DCs/trust accounts, critical system objects, non-leaf objects, account/resource groups with members, users in any global group other than their primary [S10]. | Rights in both domains | No | **High**, and new SID (old one in `sIDHistory`) (inference). **Recommend out of v1.** |
| **Attribute edit** | Modify replace/add/delete on a named attribute | Write property on that attribute (or its property set) | Replace converges; add/delete use permissive modify | **Depends entirely on the attribute.** Safe-ish: `displayName`, `description`, `title`, `department`, `company`, `manager`, `telephoneNumber`, `physicalDeliveryOfficeName`, `employeeID`, `extensionAttribute1-15` (but sync rules and Entra dynamic groups may key on these, inference). **Never via a generic edit** (all inference, well known attack paths): `nTSecurityDescriptor`, `servicePrincipalName` (Kerberoasting), `msDS-KeyCredentialLink` (shadow credentials), `msDS-AllowedToActOnBehalfOfOtherIdentity` / `msDS-AllowedToDelegateTo` (delegation), `sIDHistory`, `primaryGroupID`, `userAccountControl`, `unicodePwd`, `scriptPath`, `altSecurityIdentities`, `adminCount`, `mS-DS-ConsistencyGuid` / `msDS-ExternalDirectoryObjectId` (sync anchor, see hybrid-sync), `userPrincipalName`/`proxyAddresses` (sign-in and mail routing in Entra). The server needs an **allowlist**, not a denylist. |

### Delete and restore

| Operation | Mechanics | Rights | Idem. | Blast |
|---|---|---|---|---|
| **Delete** | LDAP Delete on a leaf. With Recycle Bin off → tombstone (most attributes and all links stripped); on → deleted-object that keeps everything for `msDS-deletedObjectLifetime` [S8]. `LDAP_SERVER_TREE_DELETE_OID` deletes a whole subtree [S7]. | Delete on the object or Delete Child on the parent; Delete Tree for tree delete [S8 constants] | Retry → `noSuchObject` | **High to Critical.** Without Recycle Bin, group memberships and most attributes are lost; a re-created object has a new SID, so every ACL naming the old one is orphaned (inference). Synced objects are deleted in Entra on the next cycle; a deleted **group** cannot be recovered there with its ACLs [S16]. Tree delete is unbounded. "Protect from accidental deletion" is a Deny Delete/DeleteTree ACE, which a server with enough rights simply gets refused by (inference). |
| **Restore (undelete)** | Modify on the deleted object, with `LDAP_SERVER_SHOW_DELETED_OID`, that contains **both** "REMOVE isDeleted" and "REPLACE distinguishedName" with the new live DN [S8]. Parent container must exist (inference). | **`Reanimate-Tombstones`** control access right on the domain NC [S8 Win32 page] plus Create Child on the target parent (inference) | Retry → `noSuchObject` (no longer deleted) | **Medium.** With Recycle Bin on, "restored user accounts automatically regain all group memberships and corresponding access rights" [S9], i.e. a restore can silently re-grant privileged access. ## Protected and privileged objects

- **Protected set** (current OS): Account Operators, Administrator, Administrators, Backup Operators, Domain Admins, Domain Controllers, Enterprise Admins, Enterprise Key Admins, Key Admins, krbtgt, Print Operators, Read-only Domain Controllers, Replicator, Schema Admins, Server Operators [S11]. Members (direct or transitive) are protected too; Account/Server/Print/Backup Operators can be excluded via `dSHeuristics` character 16 [S11].
- **Mechanism**: SDProp on the PDC emulator, every 60 minutes by default (60–7200 s configurable), resets the ACL of protected objects to AdminSDHolder's and keeps inheritance off [S11]. It sets `adminCount=1` on them; when a user leaves the protected group, `adminCount` and the disabled inheritance stay behind (inference, widely documented but not on [S11]). So `adminCount=1` over-reports "privileged", which is the safe direction for a guard.
- **Consequence for the server** (inference): for a least-privilege service account delegated on OUs, writes to protected objects already fail with `insufficientAccessRights`. The server should still check first and refuse with a clear message ("target is a protected/tier-0 object"), because (a) a misconfigured service account might be a Domain Admin, (b) operator groups can be excluded from protection, and (c) group *membership* changes are authorised by the group's ACL, so adding someone to a non-protected group that is itself nested into a protected one is not caught by AdminSDHolder until SDProp next runs.
- **Simple guard** (inference): refuse a write when the target has `adminCount=1`, or its `objectSid` RID is < 1000 (built-ins), or (for membership) the group is in the protected set or `memberOf` (transitive, via `LDAP_MATCHING_RULE_IN_CHAIN`) reaches one, or `isCriticalSystemObject=TRUE`. Also: never target `userAccountControl` & `SERVER_TRUST_ACCOUNT` (DCs).
- Sync note: Connect/Cloud Sync filter out `isCriticalSystemObject=TRUE` objects (Administrator, Domain Admins, Enterprise Admins), **but members of those groups still sync** [S16].

## No-idempotency hazards and replication

- **No idempotency keys.** Same rule as the siblings: never auto-retry. The safe recovery after a lost response is: re-read the target by `objectGUID` (stable across rename/move, inference), decide whether the write landed, report that.
- **Converging writes**: disable/enable (bit set), unlock, must-change, attribute replace, membership with permissive modify, PSO link with permissive modify.
- **Non-converging writes**: create (dup), move/rename/delete/restore (target DN gone), password reset (side effects on `pwdLastSet`, history).
- **Read-modify-write races**: `userAccountControl` and `gPLink` are whole values. Two writers with stale reads clobber each other. Delete-old/add-new in one Modify fails cleanly if the value moved (inference from [S18]).
- **Replication**: each write lands on one DC. Reads from another DC can be stale. Password changes are replicated preferentially to the PDC, and lockout is processed there [S15]. Cross-domain moves must go to the source RID master [S10]. Suggest: send writes to the PDC emulator of the object's domain, and read back from the same DC (inference; ties into the map's "cross-domain writes" open question).
- **Sync**: AD writes on synced objects reach Entra on the next sync cycle, not immediately (see [hybrid-sync.md](hybrid-sync.md)). A tool that says "done" after an AD disable should say the Entra side follows on the next cycle.

## Candidate risk clusters (suggestion for the capability map, not a decision)

Read-only stays the default. Each cluster is one risk an operator can reason about ("can the client do X?"). Names follow the sibling `kebab-case` capability style.

|---|---|---|
| `ad-account-state` | disable, enable, unlock, must-change-at-next-logon, account expiry | Reversible, converging, no new principals. Only UAC bit 0x2 is ever touched. |
| `ad-passwords` | admin password reset (± must-change) | Credential takeover of the target; secret handling. Must never be bundled. |
| `ad-group-membership` | add/remove member of **non-protected** groups | Main escalation path; converges with permissive modify. |
| `ad-objects` | create user/computer/group, rename, move within a domain, allowlisted attribute edits | Inventory and lifecycle; changes GPO scope and sync scope but not secrets. |
| `ad-delete` | delete (leaf only, no tree delete), restore from Recycle Bin | Irreversible without Recycle Bin; cascades to Entra; restore re-grants access. |
| `ad-gpo-links` | link/unlink/enable/disable/enforce GPO links, block inheritance | Policy scope over whole subtrees. |
| `ad-password-policy` | PSO create/edit/apply | Weakens or strengthens credential policy for groups of users. |
| *never exposed (recommend)* | writes to protected/tier-0 objects or protected-group membership, UAC bits other than disable (delegation, preauth, passwd-not-required), SPN, key credentials, RBCD, sIDHistory, ACLs, cross-domain move, tree delete, AdminSDHolder, dSHeuristics, GPO creation/content, schema/config, trusts, MachineAccountQuota | Tier-0 or forest-wide, mostly irreversible. Leave to the console. |

Server-side guards to consider on top of the flags (suggestions): one object per write call (no filter-selected fan-out, unlike falcon's filter-delete trap); address targets by `objectGUID`; a precondition read and a tier-0 refusal before every write; CAS-style Modify for whole-value attributes; never send `TREE_DELETE`; send writes to the domain's PDC emulator and return which DC took the write; for moves, warn when the target OU differs in sync scope from the source (if the server can know sync scope at all, see questions); for password reset, prefer generating the password server-side over accepting one from the client.

## Open questions

- **Password reset input:** should the client be allowed to supply the new password (it then sits in the model transcript), or should the server only generate one and return it once (and/or always set must-change)?
- **Tier-0 guard:** hard-coded refusal, or its own capability for operators who want the client to manage admin accounts?
- **Sync-scope warning on moves:** Connect Sync's OU filter lives on the sync server, not in AD or Graph ([hybrid-sync.md](hybrid-sync.md)); can the server know it (operator-supplied list of synced OUs?) or only warn generically?
- **Attribute allowlist:** fixed in code, or operator-configurable per deployment?
- **Write target DC:** always the PDC emulator of the object's domain, or the DC the reads come from? Ties into the map's "cross-domain writes" question.
- **Lab checks needed:** exact error when `lockoutTime` is written with a non-zero value; whether a reset with `POLICY_HINTS` and an identical password fails; whether `adminCount` really stays set after removal from a protected group on current OS versions.
